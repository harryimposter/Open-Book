Open Book · the implementation engine

Idea to implementation,
rule by rule

An idea arrives with a list of possible structures. For each client, the engine picks one of them and writes it into the email. This document lays out exactly how it does that, as numbered rules. Each rule is given in plain words first, then as the rule the code actually runs, then with a real example from the live board.

Every number here was read back from the running engine (expressions.js, mapping.js, data.js, openbook.js, email.js, scanner.js) against the 20-Aug-2026 board and the nine seed books. Where the code does something odd, this document says so rather than smoothing it over.

The job

What goes in, what comes out

The engine never invents a product. The desk writes a menu of structures on each idea. The engine's whole job is to choose from that menu for one client, then word the choice with concrete terms.

In · from the idea
FieldWhat it is
structures[]The menu, e.g. Phoenix autocall · Cash-secured puts · Reverse convertible · Zero-cost collar · Direct equity. Order matters (Rules 1, 6, 7).
naturalExpressionThe desk's headline structure. If missing, the first item on the menu.
tradeStatementThe desk's one-sentence recommendation, shown on the card.
ticker · sector · levelsUsed to fill in example terms (Rule 10).
In · from the client
FieldWhat it is
classificationRetail or Professional: decides what they can hold (Rule 4).
riskFree text such as "Growth, with income needs". Parsed into a mandate (Rule 3).

Out

One structure per client (the best implementation), a 0–100 suitability score for it, and a finished sentence: "For your book I'd implement this as a … For example: …".

The whole pipeline

Eight steps, run for every idea × every client

Step 7 (the gate) runs separately from steps 4–6 and reads only the first item on the menu. Rule 7 explains why that matters. Rule 13 covers the second source of implementations: the portfolio scan, which writes its own menus from the client's holdings.

Rule 1 · the menu

The desk writes the menu, derivatives first

In plain words

Every idea lists several ways to express it. By house style the first one is an option, structured or OTC construction, and plain shares or bonds come further down as alternates.

The exact rule

naturalExpression = idea.naturalExpression || structures[0] || "Direct equity". The engine can only ever choose something that is on structures[]. It never adds a product.

Live example

Nvidia into earnings: Call spread · Zero-cost collar · Call overwrite · Buffered note · Direct equity. The natural expression is the call spread.

Why the order is a real decision

The order is used twice. The first item is what the regulatory gate tests (Rule 7). When two products tie on score, the one listed earlier wins (Rule 6). Reordering the menu can change which clients see the idea and what they are offered.

Consequence

If a product is missing from the menu, no client can be offered it. A retail client with an OTC-only menu has nothing to choose from (Rule 8).

Rule 2 · names to products

Every name on the menu becomes one of 53 catalogued products

In plain words

The desk writes names freely ("Covered call", "Call overwrite", "Covered calls"). Before scoring, each is translated to a single catalogue entry, such as call-overwrite.

The exact rule

  1. Lower-case and trim the name.
  2. Look it up in a fixed alias table (72 exact spellings).
  3. If not found, run a keyword ladder top to bottom. The first match wins.
  4. If nothing matches, the product is unresolved: it scores a flat 70 for every mandate and gets generic wording.
keyword ladder (first match wins, abbreviated): "risk reversal" | "seagull" → fx-risk-reversal ← FX rules run first, even for equities "strangle" | "straddle" → fx-strangle "fx" + "spread" / "fx" + put|call → fx-option-spread / fx-option "collar" → zero-cost-collar "halo" → halo-basket "accrual" → range-accrual "buffer" → buffered-note "revcon" | "fcn" → reverse-convertible "capital-protected" → capital-protected-note "autocall" | "acm+" | "phoenix" → phoenix-autocall "covered call" | "overwrite" → call-overwrite "call spread" → call-spread … bonds, ladders, trims, baskets … "structured" | "note" → structured-note ← catch-all for any "… note" "etf" | "fund" | "index" → index-core "direct" | "equity" | "shares" → direct-equity ← catch-all for anything with "equity"

Rule 3 · the mandate

Each client is boiled down to one of three mandates

In plain words

The client's risk description is read for keywords and becomes growth, income or preservation. That one word decides which products score well.

The exact rule

Two passes over the text: a level and a tilt. Then: income tilt → income; preservation tilt or conservative level → preservation; growth/aggressive → growth; anything else (moderate, balanced) → income. Unreadable text falls back to the client's goal targets.

Rule 4 · who can hold what

Retail clients never get an OTC product

In plain words

Every product falls in one of three classes. Professional clients can hold all of them. Retail clients can hold plain securities and packaged notes, but not bilateral OTC contracts.

The exact rule

Before scoring, remove every menu item whose class is otc if the client is Retail. Professionals keep the full menu.

ClassRetail?Products in the catalogue
Non-complexYesDirect equity, ETFs and baskets, govt/IG bonds, ladders, T-bills, gold ETC, hedged share classes, trims, harvests, bond swaps
StructuredYesStructured note, buffered note, capital-protected note, autocall (ACM+/Phoenix), reverse convertible, HALO basket, leveraged certificate
OTCNoCall spread, collar, covered call, protective put, cash-secured puts, prepaid variable forward, gold accumulator, FX forward/collar, DCD, FX options, spreads, risk reversals, strangles
Private(qualified only)Private markets, private real estate
Packaged vs bilateral

A structured note is a security with an ISIN, so a retail client can buy it (after an appropriateness check). An OTC option is a contract with the bank, so it needs professional classification.

Rule 4 · a caveat worth knowing

There are two classifiers, and they disagree

The scorer and the gate (mapping.js) classify by searching the raw name for keywords (data.js). The email picker (openbook.js) classifies by the resolved product from Rule 2 (expressions.js). On today's board they disagree on eight names, and a ninth (Digital put) is wrong in both.

Rule of thumb until this is fixed

Trust the class shown in the email (the resolved product). It is right more often. Where the desk writes a new product name, check that it resolves (Rule 2) before relying on either.

Rule 5 · scoring

Each remaining product gets a 0–100 suitability score for the mandate

In plain words

Every catalogue product carries a small rating for each mandate: how well it serves growth (directional), income (coupon) and preservation (protection). Products whose style matches the mandate get a small bonus. The rating is stretched to 0–100.

The exact rule

Rating 0, 1 or 2 per mandate, from a fixed table. Bonus: +0.5 protective product for preservation, +0.3 coupon product for income, +0.3 directional product for growth. Unresolved product: rating 1, no bonus.

implFit  =  clamp( 0, 100, round( 40 + 30 × ( rating + bonus ) ) )
rating 0 → 40rating 1 → 70rating 2 → 1002 + bonus → still 100 (capped)
Protective (+0.5 for preservation)

Capital-protected note, zero-cost collar, buffered note, protective put, prepaid variable forward, FX forward/collar, currency-hedged sleeve

Coupon (+0.3 for income)

Autocall (ACM+/Phoenix), reverse convertible, HALO basket, call overwrite, DCD, range accrual

Directional (+0.3 for growth)

Direct equity, thematic basket, equal-weight index, leveraged certificate, call spread, index core, FX option, FX option spread, FX risk reversal

Because the score is capped at 100, the bonus only changes the result when the base rating is 0 or 1. That is why so many products tie at 100, which is what makes Rule 6's tie-break matter.

Rule 6 · the pick

Highest score wins; on a tie, the one listed first

In plain words

Walk down the menu in order, keep the best score seen so far, and only replace it with a strictly higher score. The result is the client's best implementation.

The exact rule

for s in structures: if tradable(s) and implFit(s) > best: best = s. The engine does not look at holdings, volatility, tax or tenor when picking.

Rule 7 · the gate

If the headline product is OTC, a retail client never sees the idea

In plain words

Separately from the pick, the engine checks the idea's headline product (the first on the menu). If the client is Retail and that product is OTC, the idea's fit is set to zero and it is hidden for them, with the reason shown.

The exact rule

blocked = Retail AND isOTC(naturalExpression) → fit = 0, suppressed = true. This runs even if Rule 6 found a holdable alternative further down the menu.

Rule 8 · when nothing is holdable

No holdable product: the score falls back, and the email falls back further

In plain words

If every product on the menu is OTC and the client is Retail, there is nothing to pick. The score then grades the idea's underlying risk instead. The email offers the whole menu anyway, with a caveat that it needs professional classification.

The exact rule

Score: bestImpl = null → use the risk-suitability table below. Email: implChoices = holdable items, or if none, all items. The default is the first, and the sentence adds the OTC caveat (Rule 10).

Rule 9 · implementation feeds the fit

The pick's score is 60% of the Mandate & risk axis

In plain words

How well the best product suits the client is not just a label: it feeds straight into the client-fit score that decides whether the idea is flagged to them. A great idea with no suitable product fits worse.

The exact rule

Mandate axis = 0.6 × pick score + 0.4 × intent fit. Intent fit compares the idea's goal (appreciation, yield or protection) with the mandate. The axis is then one of four fit axes, weighted 0.294.

Rule 11 · the book hook

One extra sentence ties the implementation to the client's book

After the implementation, the email adds at most one sentence drawn from the client's actual holdings. The engine checks eight conditions in this order and uses the first that fires.

#If……the email adds
aIncome or rates idea and the client holds a rates or credit bond down ≥ 10%Swap out of that bond into current-coupon paper: bank the loss, lift the coupon.
bIncome idea and cash ≥ 8% of the book"You're also holding roughly N% in cash we could put to work here."
cThe client holds the idea's own stock and it is down ≥ 10%Harvest that loss for tax and rotate the proceeds into the idea.
dFX idea and ≥ 8% of the book is in a non-base currencySize it to the ~N% mismatch; not a directional bet.
eProtection idea and the largest single name is ≥ 12% of the bookPoint the protection at that concentration.
fIncome idea and a liability is on fileThe income can be matched against that liability.
gIncome idea and an income-per-year goal is behindGoes straight at the income target, with current vs target.
hGrowth idea and a wealth goal is behindWorks toward growing the book to the target.
Live example · Micron × Ben

Rule (b) fires: "You're also holding roughly 8% in cash we could put to work here rather than leaving it idle at the front end."

The hook is wording only. It never changes which product was picked.

Rule 12 · the human override

The Solutions desk can approve, discard or rewrite

Approve / discard

Every idea from the sweep starts approved. Solutions can discard one, and it then disappears from the Advisor view for every client. Ideas the desk drafts by hand are always approved.

Rewrite the implementation

Solutions can type their own implementation text for an idea. When present, it replaces the engine's sentence (Rule 10) in every client's email and on the card, marked "tweaked by Solutions".

Advisor choice

In the email drafter the advisor can switch to any holdable product on the menu. The engine's pick is only the default selection.

sentence  =  Solutions tweak  if present,  else  Rule 10( advisor's choice  or  engine's pick )
Precedence, simply

A human decision always beats the engine. The engine's job is to make the right answer the default, so humans only need to step in on exceptions.

Integrity

What the engine does not consider, and known quirks

Not an input to the pick

  • What the client already owns. Mitch holds 24% Nvidia at +310% and is still picked a call spread (more Nvidia). Aurora holds 25.8% Micron and is picked a Phoenix on Micron.
  • Whether an overlay is possible. Jacob is picked a call overwrite on Nvidia, which he does not own.
  • Volatility, rates, tax, tenor, base currency. None enters the pick. They live only in the desk's menu order and trade statement.
  • Whether a hedge is needed. USD-based books are picked a risk reversal for a USD hedge they don't need.

Quirks in the code

  • The gate reads only the first menu item (Rule 7), while the pick reads them all (Rule 6).
  • Two classifiers disagree on eight names (Rule 4).
  • ACM+ is treated as a Phoenix; five different notes become "structured note"; some options resolve to shares (Rule 2).
  • Ties are decided by menu order, silently (Rule 6).
  • With no holdable item, the email drafter offers retail clients OTC products with a caveat (Rule 8).
  • Call-spread wording is broken (Rule 10).
What it gets right

The pick is transparent and repeatable: one table of ratings, one formula, one tie-break. Suitability shapes the product instead of killing the idea. Every suppressed client is shown with the reason, and a human can always override.
